# Injected log delivery groups

`pipeline.NewRoutedProvider` is the injection boundary for selective log delivery on the normal, non-serverless HTTP path. Nothing in Agent startup constructs it by default. It can be constructed before the auditor starts, but the caller starts the auditor before `provider.Start`. A caller supplies complete group definitions and resolves the selected group IDs for each original record before processors can reorder records. An empty selection is invalid; intentional exclusion uses `Selection.Excluded`. A checkpointed source supplies a nonzero `Selection.Generation` that changes when the source is replaced under the same registry identifier. The caller passes `provider.GuardRegistry(registry)` to routed source launchers so source-owned `SetOffset` writes cannot bypass pending delivery.

Each group has one reliable primary and may have ordinary extra endpoints. The provider creates one existing `Sender` per group, so reliable-first and best-effort extra-copy behavior remain within that group. Distinct groups remain separate obligations even when they use the same hostname and credentials. No destination is inferred from a selection failure, and an invalid record reserves an unresolved source barrier so later records cannot move its checkpoint.

A nonempty `Group.Stream` declares that its member groups receive the same ordered encoded records with compatible batch limits and compression settings. Selecting only part of such a stream is invalid. One batch strategy serializes and compresses each shared batch once; the immutable encoded bytes are passed to each group's sender. Other streams batch separately, so partial overlap can repeat compression. MRF classification is disabled for this injected path.

## Capacity and progress

The default `logs_config.routing.max_groups` is four; it is read once when the provider is constructed. A configured higher value supports more groups, subject to an aggregate limit of 32 HTTP endpoints, including extras. The routed provider accepts at most 16 processing lanes and caps concurrent HTTP requests across all endpoints at 64. Each endpoint receives at least one request slot. The per-endpoint limit can be lower than `batch_max_concurrent_send` when the aggregate cap applies.

Ingress and processed channels each hold at most 256 record references. Each declared stream has a 128-record input and a four-payload output. Each group completion adapter holds 128 payload references. The progress ledger holds at most 4096 original-record entries and backpressures admission when full. An endpoint's destination buffer uses `logs_config.payload_channel_size`, clamped to 1–128. The existing batch byte and message limits remain in force. These limits bound queue lengths and request concurrency; they are not a measured process-memory ceiling. A stalled group can eventually exhaust shared capacity and stall otherwise available groups or unrelated sources.

The progress ledger separates admission from completion. Only terminal output from a reliable destination resolves a selected group's obligation. An optional unreliable endpoint cannot resolve it. Processing exclusions and terminal local encoding or batch losses resolve only the affected record or stream obligations. Permanent HTTP rejection retains the existing terminal-loss behavior. Retryable failures, credential waits, cancellation, and queue transfer do not resolve obligations. A source checkpoint advances only through its completed registration prefix. A completion from an obsolete source generation releases resources without advancing the replacement generation. If an earlier generation reappears while replacement records are pending, its registration is rejected and held as an unresolved barrier. Generation values need only be distinct for overlapping replacements; they need not be numerically ordered. Empty source identifiers do not share a checkpoint ledger.

`Flush` sends ordered markers through ingress, every processor, and each stream batcher. It waits until records accepted before the marker have reached a flushed batch; it does not promise HTTP completion. `Stop` closes admission, drains processor and batch stages with dispatch active, then stops group senders and completion adapters before releasing unresolved progress. If the owner cancels `DestinationsContext` after its normal grace period, routed dispatch and blocked admission cancel without acknowledging unfinished obligations. The existing auditor receives safe-prefix metadata and persists it on its normal schedule. There are no per-endpoint checkpoints, durable spool, or exactly-once guarantee. An abrupt restart can replay a pending record when a usable older checkpoint and source data remain. With no checkpoint, the existing end-mode behavior can skip pending data. Startup overrides, deleted source data, invalid registries, and unbuffered network sources do not acquire a recovery guarantee from this mechanism.
