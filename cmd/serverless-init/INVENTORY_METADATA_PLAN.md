# Plan: serverless-init inventory metadata collection

serverless-init emits `inventoryagent`-style metadata to the inventory intake
(`serializer.SendMetadata` → `datadog_agent` endpoint), tagged with a
`serverless-init` flavor so the downstream decoder routes serverless fields into
serverless tables.

The plumbing is done and merged onto this branch. This file now tracks only the
remaining work and the context needed to do it.

## What already exists (context, not work)

- Shared `inventoryagent` has neutral `Capabilities`
  (`SkipCrossProcessEnrichment`, `PayloadUUID`) and a synchronous `Submit()`.
  serverless-init supplies them via `NewServerlessCapabilities` and injects
  serverless fields + flavor through the public `Set` API
  (`cmd/serverless-init/inventory/inventory.go`).
- Core fields come free from the component's existing `initData()`; flavor is
  overwritten to `serverless-init` via `Set` (we do NOT touch the process-global
  `flavor.SetFlavor`).
- Submission: `Inject()` runs in `setup()` (enable → `Set` → `Submit()`), gated
  on `serverless.inventory_enabled` (`DD_SERVERLESS_INIT_INVENTORY_ENABLED`,
  default `false`) plus the shared `util.InventoryEnabled` parity gate inside
  the component. `Submit()` sets `LastCollect`, so the runner (wired via a
  `run()` param, `inventories_first_run_delay` forced to `0`) is naturally gated
  and does not resend every tick.
- Config schema: `inventories_*` keys no longer `full-agent-only`,
  `serverless.inventory_enabled` added, `TestServerlessConfigInit` updated,
  `all_settings.go` regenerated by the image build's `schema.codegen` stage.

Key derivation facts to reuse:
- `dd_version` / `dd_service` come from the computed tag map (`tags["version"]`
  / `tags["service"]`), NOT `conf.GetString` (no such config keys; would warn).
- `dd_env` / `dd_site` are real config keys (`conf.GetString`).
- Payload key stays `resource_id` (serverless decoder reads it literally); do
  NOT rename to `CanonicalCloudResourceID`.
- Emit only `workload_type` values in the decoder allowlist: `cloud_run_service`,
  `cloud_run_job`, `cloud_function_gen2`, `azure_container_app`,
  `azure_app_service`, `azure_function`, `gcp_cloud_function_gen1`.
- Location fields (`region`, `gcp_project_id`, etc.) are discrete keys, NOT
  parsed from the CCRID downstream — send them explicitly.

## Remaining work

### 1. Per-platform `GetInventoryData` derivation

All implementations in `cmd/serverless-init/cloudservice/inventory.go` currently
return an empty `InventoryData{}`. Fill them in per platform (CloudRun,
CloudRunJobs, ContainerApp, AppService), deriving `workload_type`, `resource_id`
(CCRID), `resource_name`, `region`, and the platform id (`gcp_project_id` or
`azure_subscription_id`) and `runtime` from each struct's environment. The
source enum already exists (`cloudservice/service.go`: `CloudRunType` =
service/function/job). Co-locate with each platform's existing tag logic.

Also-accepted-downstream nullable fields not yet on `InventoryData` or in
`buildFields` — add and emit per platform when derivable, otherwise omit:
- `parent_resource_id` — stable service CCRID for revision-capable workloads
  (e.g. Cloud Run service behind revisions).
- `deployment_id`.
- `azure_resource_group` — from Azure env/tags (subscription id already surfaces
  in `serverlessProfileTags`).

### 2. AWS MicroVM

MicroVM (Firecracker, Agent runs as init inside the VM) needs its own handling —
the "enqueue synchronously in `run()`" model is wrong for it:

- **`run()` executes at image-build time** when the platform boots the VM to
  snapshot it (`/ready` → snapshot, `/validate` → post-snapshot smoke test on an
  ephemeral VM). Submitting in `run()` would be a build-time payload.
- **Submit on start and resume, not build.** Production lifecycle hooks live in
  `cmd/serverless-init/lifecycle/server.go`: submit off `/run` (VM starting) and
  `/resume` (from suspended snapshot); `/suspend` / `/terminate` are drains;
  `/ready` / `/validate` are build-time and must be excluded. A snapshot-restored
  process resumes mid-execution and does NOT re-run `run()`, so submission must
  hang off the lifecycle hook dispatch (`handleRun` / `handleResume`).
- Some fields (instance / `lambda_microvm_id`) are only known once `/run`
  delivers them in its request body — payload can't be finalized at build time.
- `MicroVM.GetInventoryData` currently returns an empty struct. Its
  `workload_type` value depends on the downstream decoder allowlist, which does
  not yet include a MicroVM entry; derive `resource_id`, `region`, and the
  workload type once that allowlist is settled.
- Open question: is one submission per start enough, or should resume re-submit?
  (Payload is otherwise static across sends.) Decide alongside the derivation.

### 3. Tests

- Unit tests for the payload builder (field presence, core fields from reused
  `initData()`, flavor overwritten via `Set`, resource id, enablement gating).
- Test that `refreshMetadata()` does not run when cross-process enrichment is
  off, and that the payload uses the per-process uuid, not the host GUID.
- fakeintake e2e asserting the serverless payload lands with
  `flavor: serverless-init` and expected fields (at minimum Cloud Run; extend
  per `write-e2e` / `e2e-audit`).

## Downstream contract (fixed for this pass)

The dd-go `createServerlessAgentResource` decoder, its `stringFields` list, and
`validServerlessWorkloadTypes` / `validServerlessDeploymentModels` allowlists
are fixed. Reconcile fields against them; if the contract must change, that is a
later pass. `report_reason` is a bounded telemetry dimension
(`startup`/`periodic`/`refresh`), not persisted; we emit `startup`.

## Rollout

Default flip of `serverless.inventory_enabled` (from `false`) once volume is
validated, on a serverless ramp independent of the full agent. Managed
separately — out of scope for this plan.
