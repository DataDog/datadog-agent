# Pitfalls (each one cost a backtest run real time)

## Shell and git
- Run the helper scripts with `bash scripts/<name> ...` and read `$?` directly. Do not pipe them and do not rely on `PIPESTATUS` (empty under zsh). `preflight.sh auth` prints `auth: ok` or `auth: FAILED` as well.
- Chain directory changes with `&&`: `cd <worktree> && dda inv schema.codegen`. With `;` a failed `cd` runs the command in the wrong directory.
- `<dest>` for `preflight.sh worktree` may be relative; it resolves against your cwd (never against the clone).
- `<ref>` may be a branch or a SHA. To pin a historical SHA set `NO_FETCH=1` so later history is never pulled in. The `mergebase` subcommand reads PR history, so do not use it in blind backtests.
- A historical dd-source snapshot for the catalog: `bash scripts/preflight.sh catalog-commit <agent-clone> <agent-sha> <dd-source-clone>` prints the last commit STRICTLY before the agent commit's timestamp. A bare `--before=<date>` can pick a later commit from the same day.
- Do not run `git worktree list` in a shared clone: it prints every other run's worktree path. Confirm your own checkout with `git -C <dest> rev-parse HEAD`.
- `npm` in the developer shell can be an alias for a supply-chain wrapper whose environment may be missing: call `node`, `turbo` and `node_modules/.bin/*` directly, and never run an install yourself.
- A tool that edits tracked files because it detected an agent (turbo appends a block to `AGENTS.md`) is handled by reverting that file (`git checkout -- <file>`); do not unset agent-identity variables to hide the agent.
- Fresh worktrees start a cold bazel server each. Run `preflight.sh cache` once for a shared disk cache and `preflight.sh bazel-shutdown-idle` to stop idle servers left by earlier worktrees (never one that is in use); stale servers compete for memory and slow every run.

## Verify (P4/P5)
- Single entry point: `bash scripts/verify_all.sh --path A|B --pkg <pkg> --owner-dirs <dirs> --worktree <wt> --catalog-dir <dir> --out-dir <out>`. It runs gazelle first, then the gates in parallel, and prints a JSON summary. The manual steps below are what it does; use them to debug one gate.
- Gazelle can exceed a 120 s tool timeout: start `bazel run //:gazelle -- ./comp/healthplatform <owner dirs>` with run_in_background and wait for its exit line. Pass the owner component directories too for Path B. Do not run tests at the same time as gazelle.
- The renderer's printed `run_hint` is a HINT only: it assumes the flags of current main. `verify_all.sh` probes `dda inv test --help` and is the single entry point; use `run_hint` only for a one-off manual run. Probe the test runner instead of hardcoding flags: `dda inv test --help`. Current main accepts `--test-args='-test.run=^Name$ -test.v'` and `--bazel-args='--test_output=all'`; older SHAs do not ("No idea what '--test-args' is!") and use `--test-run-name='^Name$' -v`. Whatever form works, confirm the log contains `--- PASS: <name>`; filter with `grep -E -- '--- (PASS|FAIL)|PASSED|FAILED'`. Raw `go test` is not used, with one narrow exception: `gen_catalog_fixture.py` runs a scratch generator file that is never committed (it needs tags `genfixture,test`).
- Scope: `dda inv test --targets=./comp/healthplatform/issues/<pkg>` for the new package (add each owner directory you edited for Path B), then `dda inv test --only-modified-packages` for the root package. The latter is non-recursive and does NOT pick up brand-new untracked packages (verified, even after `git add -N`), hence the first command. `--targets=./comp/healthplatform` is recursive and always shows baseline failures.
- Baseline failures depend on the SHA: some SHAs fail tests in unrelated packages with "no embedded schema for ..." (run `dda inv schema.compress` if the tool says so), others pass cleanly. Never reason from the error text alone: `bash scripts/baseline_check.sh <worktree>` runs the same command in a clean worktree at the same SHA and diffs the failing test names; only NEW failures are yours.
- A `-test.run` pattern that matches nothing is a false green, and a test file that gazelle has not added to the Bazel target never runs: run gazelle first, then confirm `--- PASS: <name>` using the renderer's `integration_test_name`. The mutation check must make the same command FAIL: Path A deletes the `bundle.go` import plus the check-body mutants, Path B runs the mutant table (both in `proof-tiers.md`). Two deletion mutants are not enough evidence: every mutant is killed or listed as surviving in the PR body. Record the exit code you observe (it was 1, not 3, in practice); do not hardcode it.
- Linter: `dda inv linter.go --module=. -v --targets=./comp/healthplatform/issues/<pkg>,./comp/healthplatform` (plus owner dirs) and read the end of the output: `0 issues.` is a pass. Without `--module=.` it can exit 1 with nothing printed.

## Detection quality (P3)
- Sufficiency rubric for the "minimal host-level detection attempt" (choose `todo` only if it fails the rubric, and write down which line fails): (1) it fires exactly when the stated condition happens, not on a nearby condition; (2) it can be tested against a real object (a real temp dir, socket, variable), not only a mock; (3) it does not report on transient or unrelated causes (timeouts, restarts, a different failure that shares the symptom); (4) it states what it cannot say (for example which file or service) in the text. If 1 to 3 hold and 4 is a stated requirement left unmet, use `detection: partial`.
- `detection: partial`: put the limitation in the release note, the issue description and the PR "What does this PR do", not only in Additional Notes. The renderer writes it into the description; it is never a remediation step (every step, including step 4, is an action the customer can take). A counter that only moves in some paths is a lower bound: say so.
- Probe fidelity: when I3 says the endpoint "does not answer a request", use a real request through the existing client (it lives behind its build tag); fall back to a plain dial only when no suitable client exists, and say so in the report. A dial proves a listener exists, not that the service answers.
- Transient failures flap an issue (appears, resolves next tick, repeats). A timeout, EAGAIN, or a busy peer means "could not evaluate": return an error from `detectCondition` so active issues stay untouched and nothing new is reported. For genuinely flaky conditions set `consecutive_failures: N`.
- Hysteresis and restart: the scheduler seeds each periodic check with the persisted active ids and, on the first run, resolves every seeded id the check does not return. With `consecutive_failures > 1` a found but not yet confirmed instance returns nothing, so a restart makes a real issue vanish for one interval. The fix is stateless, and the generated check does it: an instance seen but not yet confirmed returns `errPendingConfirmation` (an error, so the scheduler leaves state untouched), and a miss resets the count, and so does a run that returns a detect error (the generated check calls `resetStreak`, so only consecutive conclusive runs confirm; inconclusive runs must not count toward a streak). Log a pending or failed run once, at one level: the scheduler already logs the returned error, so a second Warn from the check doubles the lines per onset. Do not use a "first run only" flag (the error flips it and the id resolves on the next run anyway). Persistence is a no-op on Kubernetes unless `health_platform.persist_on_kubernetes` is set, so the flap shows only where persistence is on; say that precondition, not a blanket claim. Any PR or release text that claims the issue survives or resolves across a restart because of hysteresis states that persistence precondition. Prove it with `scheduler/mock`, which models seeded ids.
- Presence gate: a cluster-wide config flag is not enough when nodes differ (mixed node pools). Require a cheap signal that this host should have the thing: list the ready-made features in `pkg/config/env` with grep before writing one. `env.IsFeaturePresent` panics before feature detection has run (tests call `env.SetFeatures`), and features are detected once at start, so a gate on one can stay false until a restart; word the PR text accordingly ("library not found", not "no hardware").
- Recovery: if the observable recovers but the consumer cached its state at startup, the impact is not fixed until a restart, but only when the dependency was absent at agent start; a long-lived client that was reachable at start reconnects on its own. Use `recovery: conditional` for that wording, or `restart`, `manual`, `automatic`. A historical signal held for a window (`hold_minutes`) uses `recovery: held_window` (the default with `hold_minutes`): the release note and the issue text say it stays active for the window after the last sighting and never that it clears on its own; the renderer rejects an auto-clear recovery or text that says so. Prefer gating the report on the consumer's own startup-cached state so the issue resolves exactly when a restart fixes the impact. Read the consumer's init path.
- Cross-package reads by string (an `expvar` name, a metric name, a map key): a rename silently kills the check. Add a test that reads the real variable, or share a constant with the owner package; a test that publishes its own copy proves nothing.
- Remediation step 1 is a literal diagnostic command the customer can paste (for example `datadog-agent status`). The Agent logs to stdout on Kubernetes, so a log step needs per-platform commands: `kubectl logs <agent-pod>` for Kubernetes, `journalctl -u datadog-agent` or the default log path per OS for hosts. Only when the file path varies by install may step 1 be a search instruction, and then it names the exact string to search (quoted) and the common default paths per OS (Linux, macOS, Windows). Set `step1_path_varies` in the spec; the renderer prints a note for a step 1 that does not follow this and `check_signal.py` check 8 warns.
- Distinct states: when the signal has states with different causes or fixes (for example the endpoint is reachable but the consumer needs a restart, versus the endpoint is unreachable), each state gets its own title, description and remediation steps and its own `issue_test.go` case. One shared text for every state misleads (check 40 warns). Classify the raw error into states in `BuildIssue`.
- Remediation claims: every command, flag, status field or UI element named in the text must exist in the tree (grep it); otherwise mark it UNVERIFIED in the PR body and word the step so it still works without it.
- Check whether a helper already exists and what it treats as "available" before writing one. The scaffold's `check_test.go` covers wiring; test `detectCondition` itself in `detect_test.go` against real objects. On macOS keep unix socket paths short: `os.MkdirTemp("", "x")`, not `t.TempDir()`.

## Choices to make from I1, not from the template
- `id_scope`: `daemonset` (default) or `host`. If the condition is per node and recovers independently, use `host`.
- `multi_instance: true` for several occurrences per host. Each instance gets its own ID; an instance a run stops returning is resolved by the scheduler. The key must be bounded: the number of distinct keys is the number of backend issues.
- `needs_config: true` when the check reads agent config (`detectCondition` is a method).
- `check_source` is the scheduler registration key (unique among periodic checks); `source` is the `Source` field value in the report.
- Severity and category are judgment calls: align severity with the nearest sibling modules of the same impact class (`repo_facts.sh` lists them) and say so; if you deviate (an unused level, for example), name the alternative and why.
- The backend keying claim (one row per issue type, or per issue ID) is UNVERIFIED: the repo has two contradictory comments. List it as an open question for every per-host or multi-instance signal.

## Path B (the owner component reports directly)
- Choose B when an existing component already knows the condition and the issue must appear and clear in step with that event, not on a separate polling interval; otherwise Path A. A fast Path A check is a different design: say which one you chose and why.
- Layout: `comp/healthplatform/issues/<pkg>/<type>_issue.go` (or `issue.go`) plus `issue_test.go` and `BUILD.bazel`; no `module.go`, no `init()`, NO `bundle.go` import. The owner component imports the issue package for the constants and `BuildIssue`.
- Keep the owner edit minimal: one observer or adapter, called from the existing detection point, not a rewrite. Define a small interface in the owner package and inject the store through it (import the `def` package only, never `impl`); the adapter calls `store.ReportIssue` with a non-empty `Id` and `ResolveIssue` on clear.
- The full owner-edit guide is `references/path_b.md`; read it before writing the owner edit.
- Id: `id_scope` has no effect on Path B. Use a stable base for a per-host singleton, `base:<instance>` for several instances; hash the hostname when the id must not reveal it. The hostname fallback (`os.Hostname()`) lives in one helper with a unit test that asserts on the helper and fails when the fallback is removed; a hash always yields a non-empty suffix, so "id is not the bare base" is a vacuous assertion. Prefer the store's `IssueDiscriminator` for per-workload or per-DaemonSet conditions; for a per-node condition do not use it, and say so in the PR body. The store rejects an empty id.
- Stale and shutdown paths: resolve ids persisted under a different id after a restart or config change, and resolve everything when the owner is disabled or stops (the scheduler does this only for Path A). Evaluate once per scan or event, at the end, so a transient flip inside one cycle does not report.
- Cancellation: check `ctx.Err()` immediately before invoking the owner callback and return without notifying; with edge-triggered state a stale notify can leave an issue active until a transition that may never come. Test it by cancelling from inside the observer or a source hook.
- Transient source errors can clear an edge-triggered issue for one scan (the next scan re-raises it as NEW with a fresh time). Document the trade-off, or skip a clear transition when a source errored with anything other than an expected "no match".
- The health platform store is an optional dependency in the owner's fx graph (optional `Requires` field or `option.Option`); test the nil path and run the fx graph test of each binary that wires the owner.
- Owner files referenced only from tagged callers need matching build tags, or `go build` and the linter under each alternate tag set (serverless, iot, cluster agent) must be run; `deps_delta.sh` must measure the owner packages too.
- Tests: adapter tests (report on detect, resolve on clear, first evaluation resolves a persisted issue, resolve persisted under another id, resolve-all on disable, nil store) AND a wiring test, which is a REQUIREMENT: it drives the real owner entry point with a fake store (recipe in `proof-tiers.md`) and covers the line that attaches the observer and the disabled-owner hook line.
- Mutants: every row of the Path B mutant table in `proof-tiers.md` is killed or listed as surviving, with a reason, in the PR body; run them with `verify_all.sh --mutation-cmd`.

## Ownership and dependencies
- CODEOWNERS and README: the renderer prints `codeowners_recommendation` and `pr_review_checklist`. Print the line in the report and list it, with the README module-table row (`comp/healthplatform/README.md`, not generated; check 39 warns), under a "Review checklist" heading in the PR body; never add the CODEOWNERS line silently. Set `co_owner` in the spec when the feature team is known. `/comp/healthplatform` belongs to fleet-remediation and covers every subdirectory, but most feature-owned sibling signals also carry a per-module co-owner line. When I1 points into a feature team's code, recommend `/comp/healthplatform/issues/<pkg> @DataDog/<feature-team> @DataDog/fleet-remediation` (outside the generated block); put the exact line in the PR body ready to paste. Interactive mode: ask. Inputs mode: do not add it, but still EMIT the exact recommended line (derived from the nearest sibling's line) in the report and the PR body as a recommendation, and record the question.
- Dependency direction: the health platform bundle also starts in the cluster agent (`cmd/cluster-agent/subcommands/start/command.go` calls `healthplatform.Bundle()`) and in builds without kubelet, docker, and similar tags. Heavy or platform-specific imports (kubelet, docker, logs internals, grpc clients) are allowed only in a file gated by the matching build tag, with a `check_noop.go` stub carrying the negated tag (same constructor, returns nil, nil). An unguarded heavy import is the defect; `check_signal.py` check 20 flags it.
- Measure instead of guessing (Path B: include the owner packages, `--owner-dirs` in `verify_all.sh`): `bash scripts/deps_delta.sh <worktree> <pkg>` compares `go list -deps` of the cluster agent binary at a clean SHA with the new package's deps under the cluster agent tags. Empty delta means nothing added. Share state through a small leaf package already linked, or inject a provider via `issues.ModuleDeps`.

## Tests (P5)
- The integration test must be able to run the module's real check through `Bundle()` (inject a short interval and a fake detector input) and assert NEW then RESOLVED plus location, source and extra on the wire, not only a synthetic runner (check 17 warns when those assertions are absent).
- Keep the Path A registration test free of any import of the issue package (check 17), and make it assert category, severity, issue name and text on the received payload.
- Gate-through-config test: enable the gate with config and environment only, start the bundle, and expect the issue on the first scheduler tick (each check runs once immediately at start). It applies to an UNTAGGED check with `consecutive_failures` 1. For a build-tag-gated check the root test target may compile the noop (it depends on the runner: confirm the tags in the log), and with hysteresis above 1 the issue cannot appear on the first tick; then rely on unit tests plus a resolve proof through `scheduler/mock` or an injectable interval and hold window. A checked-in skipped test is not proof.
- OS constraints: a tag-gated test that uses unix sockets, `Geteuid` or chmod needs a `//go:build linux` constraint when the tag is in Windows builds (the kubelet-style tags are), because the Windows client uses a named pipe.
- Never register fixed names in a test (`expvar.NewMap("x")` panics on `go test -count=2`); use unique names per test or the real variable.
- `issue_test.go` must carry the mandatory assertions: exact title, a description substring, the exact step count, the Extra fields, defaults applied for nil and empty context, empty `Id` (Path A), and the names (check 21). Extend them for every remediation branch; classify the raw error into reasons and give each reason its own branch, not the raw wrapper text.
- Do not copy a sibling's registration test that imports its own issue package: that defeats the `bundle.go` mutation guard.

## Release note and PR (P7)
- While `detection: todo`: no reno note, use the `changelog/no-changelog` label, and say in the PR body that it must not merge before the TODOs land. A release note for a feature that does nothing is noise in a published changelog.
- When detection is real (`partial` or `implemented`): re-render with `--only module,release-note`; it registers the declared check and writes the note. State the platform scope in the note (for example Linux and macOS only when the accounting is unix-only). The recovery sentence follows `recovery`; never claim auto-resolve the consumer cannot deliver.
- "What does this PR do" lists only behavior with code and tests behind it, plus any `partial` limitation. Planned or TODO items go under Additional Notes; every Additional Notes claim carries its precondition (for example a flap that needs persistence on). A test skipped for root, for an OS, or for a tag is not claimed as covered.
- Verification bullets come from `scripts/verification_bullets.py` over the FINAL logs (it flags skipped tests and marks logs with no result line UNKNOWN). Never suggest `qa/done` without real QA. Do not claim baseline failures are unrelated until `baseline_check.sh` says so. If an eslint shim was used for the catalog gates, say eslint was not run.
- Catalog text must quote safely: a value inside quotes in a template breaks if the value contains a quote, and a YAML title containing a colon followed by a space needs quoting.
- No backend service names (say "the intake") and no skill or script names in repo code, comments, or release notes (check 22), and no scaffold-voice prose (phrases like "must NOT import" written for the skill author) in committed code; the `TODO(onboardhealthsignal)` marker is allowed only while detection is a TODO.
- Dry-run and inputs mode have no branch or commits, so build the PR body from `git add -N <new files> && git diff`, write it to `<out-dir>/pr-body-<pkg>.md`, and stop. Never push. Write every deliverable out as files in the out-dir (`final.diff` for the agent repo, `catalog.diff` for the catalog slice, the CODEOWNERS recommendation in the PR body) so nothing is left only in a scratch worktree.
- The PR body is not truncated and carries no template hints (no HTML comments, no placeholder text); every section ends with complete bullets (check 41 warns). Mutation claims: never write that all mutants were killed unless each was killed by a failing test; a compile error is not a kill. List per mutant the test that failed, and the survivors.
- The PR template contains HTML comment lines that mention forms or people; drop them from the drafted body (no person names anywhere).
